# 迁移踩坑清单（KANS KOL/KOC 2026-08~09 实测）

## 🔴 会造成数据事故的

### 1. 改单选/多选字段的选项会清空整列
`PUT /bitable/v1/apps/{app}/tables/{tbl}/fields/{field_id}` 时，`property.options` **必须带上原有每个选项的 `id`**。只传 `name` 会被当成重建选项集，该字段所有已填值瞬间清空。
- 实例：给 Product 加一个「RED cleanser」选项，三张表 Product 共 8,218 格被清空（靠 dump 还原）。
- 正确做法：先 `schema` 拿到选项 `{id,name}` 全集 → 原样带上 + 追加新选项（新选项不带 id）。
- 默认口径是**选项不自己加**；确需加选项先征得用户同意。
- 改字段「类型」是安全的，前提是该字段当前没有值。

### 2. 联动规则的匹配键不唯一 → 写错行
自动化「修改 A 表 → 查找 B 表对应行 → 回写」如果只按「日期 + 达人ID」匹配，一个达人做过多个产品时会把 A 产品数据写到 B 产品行。
- 实例：65 行内容被覆盖、21 行四键重复。修法：每条同步规则加 `Product 等于 第1步修改的记录.Product`。
- 新 Base 上线前检查所有「查找记录」类规则的匹配条件，至少要 达人+产品。

### 3. 规则回路 → 自动刷出大量空重复行
「新增/修改的记录满足条件时」触发：**条件字段本身变更且满足条件**才触发。若条件字段会被另一条规则回写，就形成回路。
- 实例：审核表「Progress=DONE 且 Expected release month 不为空」→ 自动建推进行；推进表任意改动又把 Expected release month 回写审核表 → 已 DONE 的老行"新满足条件" → 再建一行空推进行。一天造了 182 行。
- 官方防重做法：加复选框标记位（如「已建推进行」），条件 `Progress=DONE 且 标记未勾` → 新增 → 回写勾上标记。
- 条件分支/查找后判断只有「工作流」有，「自动化流程」没有。

### 4. 批量写不停规则 → 刷消息 + 连锁写
- 提醒类规则会给每个 BD 发几百条飞书消息
- 联动规则会把迁移数据二次传播（且可能写错行，见第 2 条）
- `fbase.js apply` 已内置 停→写→恢复。恢复时飞书偶发 500，脚本会重试并报告仍未恢复的规则——**看到 `!! 仍未恢复` 必须手动去开**。
- 「标 DONE 自动建子表行」这种想保留的，用 `--keep`。此时**同一 (达人+产品) 只标一行 DONE**，否则子表重复建行。

### 5. 规则内容没有开放 API
只有 `GET /workflows`（列）和 `PUT /workflows/{id}`（启停）。建规则、改规则逻辑 POST 全 404（不是权限问题）→ 只能浏览器里点。

## 🟠 会造成数据失真的

### 6. 取数方式混用
- xlsx 给原始值，gviz/CSV 给显示值，两次比对用不同方式 → 5,000+ 行假阳性
- gviz 静默截断（1,031 行只给 133 行）
- IMPORTRANGE 镜像表 API 读出来是公式文本，要去源表读

### 7. 合并键选错 → 两轮合作并成一行
按 (达人+产品) 合并时，同一达人同一产品做过两轮（不同月份/不同 BD/不同报价）会被并成一行：新一轮的报价/BD + 旧一轮的视频/发布日。
- 有视频的数据**按 Video ID 建行**；只有报价的按 达人+报价+产品+BD。
- 迁移前先统计"同键多行"的组数，给用户看几个例子再定合并规则。

### 8. 源表自身的脏数据
- 账号名和主页链接不一致（账号改名）→ 以主页链接里的 @handle 为准，列进台账
- 投流码/视频挂错达人（源表就错）→ 迁移不修，列进台账给业务确认
- `vt.tiktok.com` 短链：Video ID 公式算不出 → curl 跟 301 换成全链
- 同一视频挂在两个产品下 → 列台账，不自作主张
- Google 把 dd/mm 误转成 mm/dd；`22026` 这类年份笔误

### 9. 「更新日期」≠ 合作日期
源表的 update day 是"这条报价最后改的日子"，BD 视频发布后回来改价会刷新它（KANS 666 条里 147 条晚于实际发布）。判断合作时间用预计/实际发布日期。

### 10. 自动维护字段别手填
「历史合作费 / 历史合作 BD」这类由规则查找回填的字段，手填会被规则覆盖（3,408 行被覆盖 789 行）。迁移时留空，让规则跑。

## 🟡 操作层面的

### 11. 表已上线，同事在实时改
- 每次写之前重新 dump，不用几天前的快照（3 天内审核表 6,233→5,232 行）
- update 只改要改的字段，不要整行覆盖
- 字段会被改名（`Draft Process`→`Process`）、单选选项会被改名（选项 id 不变）→ 脚本按名字写会报 FieldNameNotFound，**每次开工先跑 schema**

### 12. 人员字段
- 应用没有通讯录权限时：用户把人加成 Base 协作者 → `fbase.js people/persons` 拿 open_id 和姓名
- 双上级/多 BD 大多是误填，迁移前问清楚
- 「上级 LM」这种按人走还是按产品走，要问

### 13. 其他技术坑
- 本机 python 直连飞书要 `ssl._create_unverified_context()`（公司代理自签名证书）；node fetch 没这问题
- 视图过滤器可以 `PATCH .../views/{view}` 改，`isEmpty`/`isNotEmpty` 不能带 value
- 一次 batch 最多 500 条
- 子表靠规则建行的，如果写主表时规则是停的，子表不会补建 → 要么单独迁子表，要么写完再对子表做一次补迁
